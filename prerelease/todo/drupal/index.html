PHPantom — Drupal¶

Known gaps and missing features in PHPantom's Drupal support. Today Drupal support is project discovery only: the web root is detected, and core, contrib, and the Drupal file extensions (.module, .install, .theme, …) are indexed past .gitignore. Nothing reads Drupal's own declarations: services, entity types, fields, routes, or hooks.

The requests in #48 are the scope of this document: the indexing it asked for first has shipped, and every Drupal-specific feature its discussion lists is one of the items below.

Drupal is built on Symfony components, so its service container and YAML files are close to what the Symfony support already reads. PHPStan's Drupal extension (mglaman/phpstan-drupal) is the checklist of what a Drupal developer expects from types; PhpStorm's built-in Drupal support is what they expect from an editor.

Items are ordered by impact (descending), then complexity (ascending) within the same impact tier.

Label Scale
Impact Critical, High, Medium-High, Medium, Low-Medium, Low
Complexity Low (mechanical/boilerplate, no design decisions), Medium (self-contained, follows an existing pattern), Medium-High (spans modules, some new design), High (shared/core subsystem, correctness or performance tradeoffs), Very High (cross-cutting architecture, wide blast radius)

DR1. Drupal demo project and a real-world baseline¶

Impact: High · Complexity: Low-Medium

Every other Drupal item is measured against this one. Without a demo project and a baseline from real code, Drupal support would be built untested and could regress silently.

  • examples/drupal/: a drupal/recommended-project site with one custom module and one theme, in the same shape as examples/laravel/ and examples/symfony/, with "Try:" comments at each site and a README listing what to try. The module declares a service, a route, a content entity type, a hook implementation (procedural and #[Hook]), and a render array with a theme hook.
  • Runtime assertions: an assertions.php that checks the demo's claims against real Drupal. Decide whether that bootstraps a kernel (core supports SQLite, so no server is needed) or only checks what can be read without booting.
  • A real-world baseline: run analyze on an actively maintained contrib module and a site build, bucket the diagnostics by cause, and file what Drupal-specific gaps they show. That ranks the rest of this document by what actually breaks.
  • What already works: the Symfony support reads some of the same shapes Drupal uses (event subscribers' getSubscribedEvents() maps, Class::method strings in YAML). Check each against the demo and note it in the README, so the items below only build what is missing.

DR2. Service IDs from *.services.yml¶

Impact: High · Complexity: Medium

$manager = \Drupal::service('acme.order_manager');

public static function create(ContainerInterface $container): static {
    return new static($container->get('entity_type.manager'));
}

A module declares its services in <module>.services.yml, in Symfony's service format. Type \Drupal::service() and $container->get() by the class the declaration names, and complete and navigate the service IDs, including @service_id arguments in the YAML. Newer code registers a service under its interface and fetches it with \Drupal::service(OrderManagerInterface::class); that ID is a class name and types as that class without any lookup.

The Symfony container reading already parses this format and follows aliases and parameter placeholders. Start by checking what it picks up from a Drupal module unchanged, then teach it where Drupal keeps the files (every enabled module's and core's *.services.yml) instead of config/services.yaml.

Where to look: src/symfony/container.rs, src/symfony/resources.rs, and PHPStan's Drupal extension (its service map).

DR3. Entity storage and entity type IDs¶

Impact: High · Complexity: Medium-High

$storage = \Drupal::entityTypeManager()->getStorage('node');  // NodeStorageInterface
$node = $storage->load($nid);                                  // ?NodeInterface

getStorage() returns the generic EntityStorageInterface, so every loaded entity is the generic EntityInterface and the methods a node or user has are reported as unknown. The entity type ID maps to an entity class and its storage handler through the entity type's declaration: the #[ContentEntityType] / #[ConfigEntityType] attribute, or the annotation older code uses. Read those statically, type getStorage(), load(), loadMultiple(), and create() from them, and complete and navigate entity type IDs. Entity queries (\Drupal::entityQuery('node'), $storage->getQuery()) take the same IDs and return IDs of that entity type.

Where to look: PHPStan's Drupal extension (its entity data repository and the storage return-type extensions).

DR4. Entity field access¶

Impact: Medium-High · Complexity: High (depends on DR3)

$tags = $node->field_tags;          // FieldItemListInterface
$title = $node->get('title')->value;

Fields are reached through magic properties and get(). A field name comes from the entity class's baseFieldDefinitions() or from configuration (field.storage.<entity>.<field>.yml in the exported config or a module's config/install). Type a field access as the field item list its field type gives (an entity reference field gives EntityReferenceFieldItemListInterface), and complete and navigate field names.

PHPStan's Drupal extension types any magic property on a fieldable entity as FieldItemListInterface without checking the name. That is the floor; reading the configuration is what lets an editor complete names and report a misspelt one.

DR5. Route names¶

Impact: Medium-High · Complexity: Medium

Url::fromRoute('acme.order_view', ['order' => $id]);
$form_state->setRedirect('acme.order_list');

acme.order_view:
  path: '/order/{order}'
  defaults:
    _controller: '\Drupal\acme\Controller\OrderController::view'

Routes are declared in <module>.routing.yml. Complete, navigate, and find references for route names in Url::fromRoute(), Link::createFromRoute(), $this->redirect(), $form_state->setRedirect(), and the menu, tab, and action YAML files, and report a name nothing declares. The _controller, _form, and _entity_form values may already navigate through the resource symbol maps that read Class::method strings in YAML; check before building anything for them. The parameter keys are the same problem as Symfony's F27.

A path parameter named after an entity type (/node/{node}) is upcast by Drupal's parameter converters, so the controller method's $node receives a NodeInterface, not the ID. Type an untyped controller parameter from the route that names it, and check a typed one against it.

DR6. Hooks¶

Impact: Medium-High · Complexity: Medium

function acme_form_alter(&$form, FormStateInterface $form_state, $form_id) { … }

#[Hook('form_alter')]
public function formAlter(array &$form, FormStateInterface $form_state, $form_id): void { … }

A hook is implemented by naming a function <module>_<hook> or, since Drupal 11.1, with a #[Hook] attribute on a method. Core and modules document each hook as a hook_<name>() function in a *.api.php file. Link an implementation to that documentation: hover shows it, go-to-definition reaches it, find references lists the implementations, and completing acme_ in a .module file offers the hooks with their documented signatures. Parameter types for an implementation that omits them can come from the documented signature.

DR7. Render arrays, theme hooks, and libraries¶

Impact: Medium · Complexity: Medium-High

return [
    '#theme' => 'acme_order_summary',
    '#order' => $order,
    '#attached' => ['library' => ['acme/order-summary']],
];
  • #theme names a theme hook a hook_theme() implementation declares, which renders templates/acme-order-summary.html.twig. Navigate from the string to both, complete it, and complete the #-prefixed variables the hook declares.
  • #type names a render or form element class (#[RenderElement('details')], #[FormElement('textfield')]).
  • Libraries in #attached name entries in <module>.libraries.yml.

The Twig support already finds templates outside Symfony, and a template's variables from the renders that name it; a theme hook's variables would be one more source of them (see src/twig/variables.rs).

DR8. Permission and configuration names¶

Impact: Low-Medium · Complexity: Medium

$account->hasPermission('administer acme orders');
\Drupal::config('acme.settings')->get('notify_email');

Permissions are declared in <module>.permissions.yml (and by permission callbacks), configuration objects in config/install and config/schema. Complete and navigate both, and complete the keys get() reads from the schema.

DR9. Drupal directories outside contrib and custom¶

Impact: Medium-High · Complexity: Low-Medium

The scan that bypasses .gitignore covers core, modules/contrib, modules/custom, themes/contrib, themes/custom, profiles, and sites under the web root. Sites also group modules by vendor (modules/acme/) or keep them directly under modules/, and profiles carry their own modules/ and themes/; a module a site's .gitignore hides in any of those places is not indexed, and its classes read as unknown. Scan modules, themes, and profiles whole.

The scan also runs only when the Drupal site is the workspace's Composer root. A workspace that holds the site beside other Composer projects, or opens a Drupal tree without a composer.json, gets none of it. Run it for each Composer project in the workspace that requires drupal/core, and give the scanned classes the same origin (project, vendor) other classes get, so completion ranks and filters them the same way.

Where to look: scan_drupal_directories in src/classmap_scanner/discovery.rs, its caller in src/indexing/init.rs, and how per-project Composer roots are handled there.

DR10. Plugin IDs¶

Impact: Medium · Complexity: Medium

#[Block(id: 'acme_order_summary', admin_label: new TranslatableMarkup('Order summary'))]
final class OrderSummaryBlock extends BlockBase { … }

$block = $this->blockManager->createInstance('acme_order_summary');

Blocks, field types, formatters, widgets, queue workers, and the other plugin types declare an ID in an attribute (or, in older code, a docblock annotation). Complete and navigate plugin IDs where a plugin manager takes one (createInstance(), getDefinition(), hasDefinition()), and in the YAML and render arrays that name them ('#type' is DR7), and type createInstance() as the plugin class.

DR11. Form and render callbacks¶

Impact: Low-Medium · Complexity: Low-Medium

$form['actions']['submit']['#submit'][] = '::submitOrder';
$form['country']['#ajax'] = ['callback' => '::updateRegions'];

#submit, #validate, #element_validate, #pre_render, #after_build, and an #ajax callback name methods of the form class as '::method', or a function or Class::method. Navigate, rename, and complete them, and report one that names nothing.

DR12. Translation placeholders¶

Impact: Low-Medium · Complexity: Low-Medium

$this->t('Order @number was placed by %name', ['@number' => $id, '%nmae' => $name]);

t(), $this->t(), new TranslatableMarkup(), and formatPlural() replace @, %, and : placeholders from the array they are given. Report a placeholder the string uses that the array does not supply, and a key the string never uses.

DR13. Module names and *.info.yml¶

Impact: Low-Medium · Complexity: Low-Medium

\Drupal::moduleHandler()->moduleExists('acme_shop');

dependencies:
  - drupal:node
  - acme:acme_shop

A module's machine name is the basename of its *.info.yml. Complete and navigate machine names in moduleExists(), getModule(), and the dependencies of an info file, and report one that names no module. Check an info file's required keys (name, type, core_version_requirement) and their shapes.

DR14. Port PHPStan's Drupal extension tests¶

Impact: Medium · Complexity: Medium

PHPStan's Drupal extension (mglaman/phpstan-drupal) is this document's checklist, but its tests are not ported, as the Symfony, Doctrine, and WordPress extensions' are (tests/phpstan_symfony/, tests/phpstan_doctrine/, tests/wordpress_stubs/). Its type tests cover \Drupal::service() and container lookups, entity storage and entity queries, field item lists, and the rule tests deprecated and discouraged calls. Port them into tests/phpstan_drupal/ the same way: the assertType() fixtures run by tests/assert_type_runner.rs, the rule tests as .fixture files, a slice of drupal/core copied by scripts/extract-framework-stubs.php, and upstream's test modules and their *.services.yml as the project. Until DR2 to DR4 ship most assertions are a // SKIP pointing at the item that covers them; file any that no item does. Rules about Drupal's own deprecations are listed in the README as not ported.

DR15. Benchmark for Drupal names¶

Impact: Low-Medium · Complexity: Low (depends on DR2)

Laravel, Symfony, and Yii have Criterion benchmarks in benches/. Once Drupal service IDs complete (DR2), add benches/drupal_completion.rs in the shape of benches/symfony_completion.rs: generate a site with many modules, each declaring services, routes, and hooks, and time completion of service IDs, route names, and hook names as each ships. Register it in Cargo.toml so benches/ci_benchmarks.py picks it up.

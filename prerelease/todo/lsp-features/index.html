PHPantom — LSP Features¶

Items are ordered by impact (descending), then complexity (ascending) within the same impact tier.

Label Scale
Impact Critical, High, Medium-High, Medium, Low-Medium, Low
Complexity Low (mechanical/boilerplate, no design decisions), Medium (self-contained, follows an existing pattern), Medium-High (spans modules, some new design), High (shared/core subsystem, correctness or performance tradeoffs), Very High (cross-cutting architecture, wide blast radius)

F7. Evaluatable expression support (DAP integration)¶

Impact: Low-Medium · Complexity: Low

Tell debuggers (Xdebug via DAP) which expression sits under the cursor during a debug session. Given a cursor position, the handler returns the expression text and range that the debugger should evaluate in the running PHP process.

LSP has no standard request for this. Phpactor uses a custom textDocument/xevaluatableExpression (advertised as experimental.xevaluatableExpressionProvider), which only its own client calls. The choice is between a custom method that our VS Code extension consumes, or the standard 3.17 textDocument/inlineValue request (InlineValueParams and inline_value_provider are available). Decide that before implementing.

Supported expression kinds¶

  • Variables: $var — return the variable name and its span.
  • Property access: $obj->prop, $this->prop — return the full member access expression.
  • Array access: $arr[0], $arr['key'] — return the full subscript expression including brackets.
  • Static property access: Foo::$bar — return the full expression.
  • Parameters: function/method parameters at declaration sites.

Why this is cheap¶

The symbol map already identifies all of these constructs with precise byte ranges. The handler is a thin layer: look up the SymbolSpan at the cursor position, check that it's a variable, member access, or subscript expression, and return the source text and range. No type resolution needed.

What this enables¶

When a user is debugging PHP with Xdebug and hovers over $user->name in their editor, the editor asks the LSP "what expression is here?" and forwards it to the debug adapter for evaluation. Without this handler, the editor falls back to selecting the word under the cursor, which gives name instead of $user->name — useless for the debugger.

F11. Windows code signing¶

Field Value
Impact Medium
Complexity Medium

macOS release binaries are signed and notarized (.github/workflows/release.yml), but the Windows packaging step signs nothing, so SmartScreen flags the binary the VS Code extension downloads. Add an Authenticode certificate (or Azure Trusted Signing) and signtool to the release workflow.

F12. IntelliJ / PHPStorm plugin¶

Field Value
Impact High
Complexity Medium-High

Create an IntelliJ plugin that depends on LSP4IJ and bundles PHPantom. Publish it to the JetBrains Marketplace. Works in all IntelliJ-based IDEs (PHPStorm, IntelliJ IDEA, WebStorm, etc.).

Approach¶

Fork clojure-lsp-intellij (MIT-licensed). It is a Kotlin/Gradle plugin that registers a language server via lsp4ij's com.redhat.devtools.lsp4ij.server extension point. Strip the Clojure-specific parts and replace them with PHPantom:

  • Register PHPantom as the language server in plugin.xml.
  • Map the PHP language and file type via com.redhat.devtools.lsp4ij.languageMapping.
  • Bundle or auto-download the PHPantom binary.
  • Add a settings page for the binary path and any PHPantom-specific options.

Scope¶

  1. plugin.xml registration. Server definition, language mapping, file type mapping (.php, .phtml, .inc).
  2. Binary management. Auto-download from GitHub Releases on first run, with a manual path override in settings.
  3. Settings UI. Binary path, PHP version override, diagnostic toggles.
  4. JetBrains Marketplace listing. Icon, description, plugin compatibility range (2024.2+, matching lsp4ij's requirement).
  5. CI. GitHub Actions workflow using gradlew buildPlugin and gradlew publishPlugin.

Why not use the built-in IntelliJ LSP API¶

IntelliJ's native LSP support (since 2023.2) is only available in Ultimate editions and is still limited in capability. LSP4IJ is free, works in all editions (including Community), and supports a broader set of LSP features. Using lsp4ij also means the plugin works in IntelliJ IDEA (for PHP projects opened there) and other JetBrains IDEs, not just PHPStorm.

F15. Go-to-declaration¶

Impact: Low-Medium · Complexity: Low

Implement textDocument/declaration to jump from a concrete method to its abstract or interface prototype, complementing the existing go-to-definition (which jumps to the concrete implementation) and go-to-implementation (which jumps from an interface to concrete classes).

Behaviour¶

When the cursor is on a method call or method name:

  1. Search for an interface or abstract class that declares a method with the same name and is in the inheritance chain of the resolved class.
  2. If found, jump to the interface/abstract method declaration.
  3. If no abstract prototype exists, fall back to the same result as go-to-definition.

Implementation¶

The existing resolve_implementation already does reverse lookups (concrete → prototype) via resolve_reverse_implementation. The declaration handler can reuse this: for MemberAccess and MemberDeclaration symbols, call the reverse-implementation resolver first. For class-level symbols, declaration and definition are the same.

Register declaration_provider in src/backend/startup.rs and wire it to a thin handler that delegates to the existing infrastructure.

F16. On-type } brace de-indent¶

Impact: Low · Complexity: Low

Extend the existing on-type formatting handler (currently triggered on \n for docblock generation) to also trigger on }, automatically de-indenting the closing brace to match its opening {.

Behaviour¶

When the user types }:

  1. From the } position, scan backward through the document text to find the matching { (tracking brace depth, skipping strings and comments).
  2. Read the indentation of the line containing the matching {.
  3. If the } line has more indentation than the { line, return a TextEdit that replaces the leading whitespace on the } line with the { line's indentation.

This is a pure text-based operation — no AST needed. Register } as an additional on_type_formatting_trigger_character alongside the existing \n.

F17. Wire class move to workspace/willRenameFiles¶

Impact: Medium · Complexity: Medium

Renaming a class's FQN via textDocument/rename already moves the file and rewrites references across the project: renaming a class's declaration accepts the full FQCN so it can move between namespaces in one step, and renaming a namespace segment rewrites every affected namespace declaration, use statement, and FQN reference while moving the PSR-4 directories to match (see build_class_move_edit in src/rename/class/ and build_namespace_rename_edit in src/rename/namespace/). What's still missing is the editor-triggered path: when the user renames or moves a PHP file in the editor's file tree (rather than through the LSP rename command), nothing updates the file's namespace declaration or the workspace's use imports.

Wire the existing move logic to workspace/willRenameFiles (declared via server capabilities workspace.fileOperations.willRename): on a file-tree rename/move, recompute the namespace from the destination path using the PSR-4 autoload map, and reuse the same reference-rewrite machinery to produce the WorkspaceEdit. The companion workspace/willCreateFiles can then insert a PSR-4-derived namespace + class stub into newly created files.

References: - Phpactor: MoveClass refactoring in the class-mover package.

F21. Static typeHierarchyProvider advertisement¶

Impact: Low-Medium · Complexity: Low

Type hierarchy (textDocument/prepareTypeHierarchy, typeHierarchy/supertypes, typeHierarchy/subtypes) is fully implemented (src/type_hierarchy.rs) and registered dynamically via client/registerCapability in initialized (src/backend/startup.rs, using type_hierarchy_registration() from server.rs), gated on the client declaring textDocument.typeHierarchy.dynamicRegistration: true. This works for every client that supports dynamic registration, but there is no static fallback, so a client that supports type hierarchy without dynamic registration, or any tool that inspects only the initialize response's static capabilities (such as a feature-conformance probe), sees no type hierarchy support at all, even though the feature works end-to-end for a real editor that does the dynamic-registration round trip.

ServerCapabilities has type_hierarchy_provider: Option<TypeHierarchyProvider>. Add static advertisement (TypeHierarchyOptions or the boolean variant) in initialize, conditional on the client not declaring dynamicRegistration: true for type hierarchy (avoid double-registering: send either the static capability or the dynamic registration, not both, per the client's declared support).

Where to look: src/backend/startup.rs (initialize, initialized), src/server.rs (type_hierarchy_registration), src/type_hierarchy.rs.

F22. Merge a namespace onto one that shares a class name¶

Impact: Low-Medium · Complexity: Medium-High

Renaming App\Internal to an App\Support that already exists now merges: the files move into the existing directory one at a time instead of the source directory being renamed on top of the destination. Where the two namespaces declare the same class name (App\Internal\Helper and App\Support\Helper both exist), the whole rename is refused with a message naming the clash, because the merge has no well-defined answer for that name — see namespace_merge_conflict in src/rename/namespace/layout.rs.

Refusing is the safe answer, not the desirable one: a user merging twenty files should not be blocked by one clash. What is missing is a partial merge that moves everything except the clashing names and leaves those behind intact. "Intact" is the hard part and the reason this is deferred rather than done:

  • The clashing class's file must keep its own namespace declaration, so that file's namespace-declaration edit has to be suppressed while its siblings' are kept. Today the namespace rename rewrites by string prefix over raw text with no per-class granularity.
  • Every reference to the clashing FQN (use App\Internal\Helper;, \App\Internal\Helper, and unqualified Helper inside the old namespace) must be left pointing at the old name. Rewriting them is what makes a naive partial merge worse than a refusal: the reference silently resolves to the other class.
  • A file holding both a clashing class and a non-clashing one cannot half-move, so it has to be reported as a clash too.
  • The classes that do move out of the old namespace stop being namespace-siblings of the ones left behind, so the files left behind need use imports added for them — the same rule build_class_move_edit already applies for a single class move.

The refusal message should then list only the names that could not move, and the response should still carry the edits for everything that could.

Where to look: src/rename/namespace/mod.rs (build_namespace_prefix_rename_edit), src/rename/namespace/layout.rs (namespace_merge_conflict, collect_merge_move_ops), src/rename/class/mod.rs (the import-adding rule to mirror).

F23. Rename a class through its XML entity-escaped occurrences¶

Impact: Low · Complexity: Medium

Rename rewrites a class, controller action, or namespace in YAML and XML files in the spelling each occurrence uses, doubled YAML backslashes included (collect_framework_name_edits in src/framework.rs). An XML attribute can also spell the separator as a character reference, App&#92;Handler&#92;Run, and neither the resource scanner nor the framework index decodes those, so such an occurrence is not found by Find References and is left behind by a rename.

The scanners would need to decode &#92;/&#x5C; while tokenising, record where each decoded character came from, and re-encode the replacement the same way when the rename writes it back.

Where to look: src/resource_navigation.rs (scan_symbols, normalize_fqn), src/framework.rs (scan_class_like_tokens, rewrite_framework_fqn_literal).

F24. Doctrine lenses miss attribute mappings and generic repositories¶

Impact: Medium · Complexity: Medium

#[ORM\Entity(repositoryClass: AccountStore::class)]
class Account {}

/** @extends ServiceEntityRepository<Account> */
class AccountStore extends ServiceEntityRepository {}

The CodeLens that links a Doctrine entity and its repository finds the pair through a YAML/XML mapping or the naming convention (App\Entity\User and App\Repository\UserRepository). The modern form above is not read in either direction. Doctrine ORM 3 dropped YAML mappings, so #[ORM\Entity(repositoryClass: ...)] is how most projects name a repository, and the repository's own @extends ServiceEntityRepository<Account> (or the class it passes to parent::__construct()) names its entity. A pair that breaks the naming convention gets no lens.

The attribute needs reading at parse time, with its class name resolved the way the parser resolves extends, into ClassInfo (a field every class pays for, or a slot in an optional per-class box). The entity-to-repository direction can then read the entity's ClassInfo, and the repository-to-entity direction the first generic argument of its ServiceEntityRepository/EntityRepository ancestor in extends_generics. T45 needs the same attribute.

Where to look: src/framework.rs (doctrine_repository_fqns_for_entity, doctrine_entity_fqns_for_repository), src/parser/classes/class_likes.rs (extract_class), src/parser/attributes.rs.

F25. Names a PHP configurator spells as strings¶

Impact: Medium · Complexity: Medium

return static function (ContainerConfigurator $container): void {
    $container->services()->load('App\\Service\\', '../src/Service/');
};

return static function (RoutingConfigurator $routes): void {
    $routes->add('legacy', '/legacy')
        ->controller('App\\Controller\\DemoController::legacy');
};

The same names in services.yaml and routes.yaml take part in rename and navigation: a namespace-prefix key follows a namespace rename, a resource: path follows its directory, and a Class::method controller string navigates and renames with the method. Written in a PHP configurator they are plain strings. load()'s namespace prefix and resource path, and a controller given as one Class::method string, need reading from the AST where the receiver is confirmed as a configurator (TypedReceiverSite), the way the container's service IDs are, and feeding to the framework index the YAML occurrences are kept in. Sidux's

398 did this by scanning the PHP text.¶

Where to look: src/framework.rs (FrameworkReference, collect_framework_name_edits), src/symbol_map/extraction/symfony.rs, src/blade/typed_receiver.rs.

F26. Symfony service IDs a bundle or a definition API declares¶

Impact: Low-Medium · Complexity: Medium

Service IDs and container parameters are read from the application's YAML, XML, and PHP configurators. A bundle's own declarations, and the ones a kernel or an extension makes through the ContainerBuilder API (register('app.mailer', …), setAlias(), setParameter() on a builder, setDefinition()), are not, so those names neither complete nor navigate, and only names under the application's own app. prefix can be reported as undeclared. Two reading shapes are missing too: a configurator's ->parent('app.base'), and the %name% placeholders in a string a configurator passes as an argument (->args(['%app.sender%'])).

Reading the installed bundles' Resources/config/ would also let the unknown-ID check judge names outside app.; it has to stay cheap enough for a project with dozens of bundles.

Where to look: src/symbol_map/extraction/symfony.rs (symfony_receiver_method), src/symbol_map/string_keys.rs (ReceiverClass), src/symfony/.

F27. Symfony route parameters¶

Impact: Medium · Complexity: Medium

Blocks full Symfony support: the README keeps Symfony marked as partial until this lands.

#[Route('/post/{slug}', name: 'blog_post')]
public function show(string $slug): Response { … }

$this->generateUrl('blog_post', ['slug' => $post->getSlug()]);

{{ path('blog_post', {slug: post.slug}) }}

Route names complete and navigate, but the parameters a route's path declares do not: the slug key above neither completes from {slug} nor navigates to it. Laravel completes the keys of route('name', [...]) from the URI it keeps with each route name (completion/laravel_route_params.rs). A parameter only means something under its route, so it does not fit a StringKey span on its own: a key spelled as one global name would merge every route's id. It needs the path kept beside each route declaration (the attribute's path, the YAML path:, the XML path attribute, the configurator's second argument, and the class-level prefix in front of a method's path), and the parameter array of each generateUrl(), redirectToRoute(), generate(), path(), and url() call read against it.

Where to look: src/symbol_map/extraction/symfony.rs (emit_symfony_route_spans), src/symfony/routes.rs, src/completion/laravel_route_params.rs.

F28. Symfony route names a loader composes¶

Impact: Low-Medium · Complexity: Medium

A route's name is read where it is declared: a #[Route] attribute, with its class's name prefix, a routing YAML or XML entry, or a routing configurator's add(). A few names are put together elsewhere, and are missed:

  • an import's name_prefix: in the routing YAML (or ->namePrefix() in a configurator), which prefixes every route it loads, attribute routes included;
  • the routes a collection's add() declares under its $routes->collection('blog_') prefix;
  • the @Route docblock annotations older applications still use;
  • the routes bundles declare in their own routing files, which is also why only names under the application's own app_ prefix are reported as undeclared.

Where to look: src/symfony/routes.rs, src/symbol_map/extraction/symfony.rs, src/symbol_map/string_keys.rs (ReceiverClass::RoutingConfigurator).

F29. Report Symfony translation keys nothing declares¶

Impact: Medium · Complexity: Medium

Blocks full Symfony support: the README keeps Symfony marked as partial until this lands.

$translator->trans('demo.titel'); // a typo of demo.title

Translation keys complete and navigate within their domain, but one that no catalogue declares is not reported. Service IDs and routes are only judged under the application's own app. and app_ prefixes; translation keys have no such convention, so judging needs a fuller picture of what is declared:

  • the catalogues installed bundles ship (validators, security, and any bundle's own domain), which a key in the same domain may come from;
  • the project's messages that are their own translation (trans('Save') with no catalogue entry translates to Save), which only a domain the project declares keys in, and keys that look like keys, can tell apart.

A starting point is to judge only domains no installed package ships a catalogue for, and only keys spelled like dotted identifiers.

Where to look: src/diagnostics/laravel_string_keys.rs (CheckedStringKind::of), src/symfony/translations.rs.

F30. Symfony translations outside YAML, XLIFF, and the trans filter¶

Impact: Low-Medium · Complexity: Medium

Catalogues are read when they are YAML or XLIFF files under a translations/ directory, and keys are read from a translator's trans(), TranslatableMessage, t(), and Twig's trans filter. These are missed:

  • PHP catalogues (translations/messages.en.php returning an array). They are PHP, so they have to be read from the AST during symbol-map extraction, which does not know the file's path today. The array walk can share virtual_members/laravel/array_file.rs (for_each_entry, dotted_key) with Laravel's trans_keys.rs.
  • JSON, CSV, INI, and the other formats Symfony loads, and catalogue directories configured under framework.translator.paths.
  • The catalogues installed bundles ship, so their keys neither complete nor navigate.
  • Twig's {% trans %}…{% endtrans %} block and its from 'domain' clause.
  • Keys in other domains by convention: validation constraint messages (validators) and form labels under a form's translation_domain.

Where to look: src/symfony/translations.rs, src/symbol_map/extraction/symfony.rs (push_translatable_spans).

F31. Symfony Twig templates outside templates/¶

Impact: Low-Medium · Complexity: Medium

A template is known by its path under the project's templates/ directory, and a bundle override under templates/bundles/AcmeBundle/ by its @Acme/ name as well. These are missed:

  • the directories config/packages/twig.yaml adds or moves the default one to (default_path:, and paths: with or without a namespace);
  • a project's own bundle's templates (src/Resources/views/, or a bundle's templates/);
  • the templates installed bundles ship, both under their @Twig-style namespace and the ones registered without one, such as the form themes twig-bridge provides (bootstrap_5_layout.html.twig), so their names neither complete nor navigate.

A name under a namespace is never reported as unknown, but one in an extra directory paths: adds without a namespace is, so reading twig.yaml matters most.

Where to look: src/twig/roots.rs (TwigRoots::discover, TwigRoots::template_names).

F59. Send Twig, YAML, and XML documents to the server¶

Impact: Medium-High · Complexity: Medium

Neither editor extension sends the server anything but PHP and Blade, so everything PHPantom reads inside a Twig template or a YAML or XML file (template names, route names, translation keys, service IDs, parameters, configuration keys) never reaches a VS Code or Zed user. Those files are still indexed from disk, so the PHP side of each name works, but completion, go-to-definition, references, and rename started from the file itself do not.

Joining those languages has to add to what the user already has, never replace it: the file keeps its language, and the Twig, YAML, and XML extensions keep serving it. Taking a file over (mapping .html to Twig with Zed's file_types, say) trades the HTML, CSS, and JS support it had for the one syntax PHPantom answers, and is not an option. .html stays out for the same reason; a project whose templates are .html renames them to .html.twig.

What is needed:

  • Answer only what the server owns in those documents. The formatting, range_formatting, and semantic_tokens_full handlers in src/server.rs do not check the document's kind, so a client that sends a template would be offered PHPantom as its formatter and its highlighter. Semantic tokens are single-winner in VS Code, so they could displace the Twig extension's highlighting. For a resource document, every request but completion, hover, definition, references, rename, and the code actions that name a string key answers nothing: formatting, semantic tokens, folding, document symbols, inlay hints, code lenses, signature help, and highlights included.
  • The VS Code extension. Add twig, yaml, and xml to the document selector in src/client.ts (both the folder-scoped and the on-disk selectors), with an onLanguage: activation event each in package.json. Its hover and document-symbol middleware must leave those documents alone.
  • A pull request to zed-extensions/php. Add Twig, YAML, and XML to languages under [language_servers.phpantom] in extension.toml, with language_ids (twig, yaml, xml). Those languages come from other extensions, so confirm that Zed starts the server for a language another extension defines before opening it.

Where to look: src/server.rs, Backend::is_resource_uri (src/twig/mod.rs), the VS Code extension's src/client.ts and package.json, and the Zed PHP extension's extension.toml.

F32. Report unknown Symfony names in Twig templates¶

Impact: Medium · Complexity: Medium

Blocks full Twig support: the README keeps Twig marked as partial until this lands.

{% include 'partials/crad.html.twig' %}
<a href="../{{ path('app_hme') }}">Home</a>

An unknown template or app_ route is reported where PHP names it, but not in a Twig template: diagnostics are not run on resource documents at all. They need scheduling for a Twig file the way a PHP file's are, the string-key check reading the template's resource symbol map, and the "Create missing template" quick fix offered there too. A template being created or deleted should also refresh the open files that name it.

Where to look: src/backend/documents.rs (did_open, did_change for resource documents), src/diagnostics/laravel_string_keys.rs, src/code_actions/create_missing_view.rs.

F58. Configured Twig roots and namespaces¶

Impact: Low-Medium · Complexity: Medium

Twig roots are discovered from the names templates reference (src/twig/roots.rs), which cannot find everything:

  • Namespaced names. {% include '@admin/menu.html' %} names a root through a namespace the loader registers at runtime ($loader->addPath($dir, 'admin')), and the namespace says nothing about which directory it maps to.
  • Roots no template references into. A directory whose templates are only ever rendered from PHP, and never extended or included by another template, is not discovered, so its names neither navigate nor count as known.

Where the loader's arguments are literals (new FilesystemLoader(__DIR__ . '/views'), addPath('templates/admin', 'admin')), read them statically first. For the rest, add a [twig] section to .phpantom.toml: paths (highest precedence first) and namespaces (admin = "templates/admin"), merged with the discovered roots.

Where to look: src/config.rs, src/twig/roots.rs (TwigRoots::discover), src/twig/mod.rs (TwigState).

F34. Template names a PHP wrapper builds¶

Impact: Medium · Complexity: Medium-High

public function render(string $template = 'index', array $data = []): string
{
    return $this->twig->render($template . '.html', $data);
}

app(RenderService::class)->render('product', $data);

Applications and frameworks rarely call Twig with a literal: they pass a short name to a wrapper that adds the extension (or a theme directory) and renders it. The literal at the call site names a template, but nothing says so. The wrapper's parameter needs marking as a template name, together with how the wrapper completes it (the suffix it appends, the directory it prepends). That could be a docblock type in the spirit of Laravel's view-string, or a .phpantom.toml entry for wrappers a project does not own (OpenCart's Loader::view()).

Where to look: src/symbol_map/extraction/symfony.rs (symfony_receiver_method), how view-string parameters are read for Laravel views. TwigStan's context collectors (the ones that find render() calls and #[Template] returns) show which call shapes it recognises as rendering a template.

F35. Suggest a close name for an unknown template or view¶

Impact: Low-Medium · Complexity: Low

return $this->render('blog/shw.html.twig');   // blog/show.html.twig exists
return view('emails.welcom');                  // emails.welcome exists

An unknown Twig template or Laravel view offers only "Create missing template/view", which is the wrong fix for a typo. Offer the closest declared names first ("Change to 'blog/show.html.twig'"), ranked by edit distance and limited to a few, the way Symfony's language tools do. Both kinds already go through one collector, so one change serves both.

Where to look: src/code_actions/create_missing_view.rs.

F36. Twig block navigation¶

Impact: Medium · Complexity: Medium

Blocks full Twig support: the README keeps Twig marked as partial until this lands.

{% extends 'base.html.twig' %}
{% block body %}…{% endblock %}

A {% block %} in a child template overrides the block of the same name in the template it extends, possibly several levels up, and {{ block('x') }} and {{ parent() }} refer to them. None of that navigates. It is the Twig counterpart of Blade's section and stack navigation (blade/blocks.rs), and the extends links are already TwigTemplate spans, so it needs the blocks each template declares and a resolver that walks up the chain: go to the overridden block, find the overrides of a parent's block, and complete the block names a child can override.

Where to look: src/twig/templates.rs, src/blade/blocks.rs, src/blade/block_index.rs.

F37. Twig template variables¶

Impact: Medium · Complexity: Medium-High

Blocks full Twig support: the README keeps Twig marked as partial until this lands.

return $this->render('post/show.html.twig', ['post' => $post]);

{{ post.title }}

The variables a template receives come from the keys every render() of it passes, the names a #[Template] action returns, Twig's globals, and the {% types %} tag. Completing and hovering those names is feasible from the call sites alone, the way Blade's call-site inference collects a template's variables (blade/call_site_inference.rs). F39. Report unknown Symfony configuration keys¶

Impact: Medium · Complexity: Medium-High

# config/packages/acme_demo.yaml
acme_demo:
    mailer:
        dns: smtp://localhost # a typo of dsn

A key the project's own TreeBuilder schema declares completes and navigates, but one it does not declare is not reported. Judging needs the schema's open nodes, which the walk does not record today: a variableNode() and a prototyped node take any key, ignoreExtraKeys() lets an array node take any, canBeEnabled() and canBeDisabled() add an enabled key no string names, and fixXmlConfig() lets the YAML spell a key in its plural. Diagnostics are not run on resource documents yet either (see F32).

F40. Symfony configuration schemas the TreeBuilder walk misses¶

Impact: Low-Medium · Complexity: Medium

Keys are declared by a chain of node builders in a getConfigTreeBuilder(), and read from YAML under config/packages/. These are missed:

  • the keys under a prototyped node (a map of named entries), whose path holds a name the configuration chooses;
  • a bundle's schema in AbstractBundle::configure(DefinitionConfigurator $definition), whose root is the bundle's extension alias;
  • nodes a helper method builds and append() adds, and node definitions held in a variable between statements;
  • installed bundles' schemas (framework, doctrine, twig), so their keys neither complete nor navigate;
  • configuration written in PHP (config/packages/*.php) or XML.

Where to look: src/symfony/config_tree.rs, and PHPStan's Symfony extension (Type/Symfony/Config/), which tracks the same parent each builder's end() returns.

F41. Symfony forms and validation beyond a form type's own data class¶

Impact: Low-Medium · Complexity: Medium

A form field navigates to the property of the data_class its form type's configureOptions() sets, and a validation mapping's properties: to the class's properties. These are missed:

  • a data_class a parent form type sets, or one passed to createForm() in its options;
  • a field the property accessor reaches through a getter, an isser, or a hasser rather than a property, which navigates nowhere;
  • the fields of a child builder, $builder->get('address')->add('street'), which belong to the child's data class;
  • a validation mapping's getters:, which name the get, is, or has method they read by its property-like name;
  • in YAML, the constraints another constraint's options hold (All, Sequentially, AtLeastOneOf), and constraints under a namespaces: alias.

Where to look: src/symfony/forms.rs, src/symfony/validation.rs.

F42. Symfony console arguments and options¶

Impact: Medium · Complexity: Medium

protected function configure(): void
{
    $this->addArgument('name', InputArgument::REQUIRED)
        ->addOption('dry-run', null, InputOption::VALUE_NONE);
}

protected function execute(InputInterface $input, OutputInterface $output): int
{
    $input->getArgument('nmae');   // a typo, not reported
    $input->getOption('dry-run');  // mixed, should be bool
}

A command declares its arguments and options in configure(), or as the #[Argument] and #[Option] parameters of an invokable command's __invoke(). The names getArgument(), getOption(), hasArgument(), and hasOption() take neither complete nor navigate, an undefined one is not reported, and the value is mixed where the declaration settles it: bool for VALUE_NONE, an array for IS_ARRAY, and nullable unless the argument is required or the option has a default. The extension's fixtures are tests/phpstan_symfony/data/Example*Command.php for the types and the tests/fixtures/phpstan_symfony/ fixtures on rules/Symfony/ExampleCommand.php for the checks.

Where to look: src/symbol_map/ (CommandOwnParam), src/virtual_members/laravel/ (the Artisan signature parsing), and PHPStan's Symfony extension (Rules/Symfony/Undefined*Rule, Rules/Symfony/Invalid*DefaultValueRule, Type/Symfony/InputInterface*Extension).

F43. Doctrine entity fields in repository calls¶

Impact: Medium · Complexity: Medium-High

$users->findByEmail($email);                    // unknown method
$users->findBy(['emial' => $email], ['name' => 'ASC']); // a typo, not reported

An entity's repository answers findBy<Field>(), findOneBy<Field>(), and countBy<Field>() for each of the entity's fields, and its findBy(), findOneBy(), count(), and findBy()'s $orderBy take field names as array keys. None of the magic methods resolve, and the keys neither complete, navigate, nor get checked. The magic methods are virtual members of the repository, the way Eloquent's are, which needs the repository's entity (T45). The keys are member references to the entity's mapped properties, the same member spans a form field and a validation mapping record.

The fields come from the entity's mapping: #[ORM\Column], #[ORM\Id], and the relation attributes, or the XML mapping the CodeLens already reads.

The extension's fixtures are magic_repository_method_call.fixture and repository_method_call.fixture in tests/fixtures/phpstan_doctrine/.

Where to look: src/virtual_members/, src/framework.rs (the Doctrine mapping index), and PHPStan's Doctrine extension (Reflection/Doctrine/EntityRepositoryClassReflectionExtension, Rules/Doctrine/ORM/RepositoryMethodCallRule).

F44. Doctrine DQL and query builder strings¶

Impact: Medium · Complexity: High

$em->createQuery('SELECT u FROM App\Entity\User u WHERE u.emial = :e');
$qb->select('u')->from(User::class, 'u')->where('u.email = :e')->getQuery()->getResult();

DQL names entity classes and their fields in strings, directly or through a query builder's select(), from(), join(), and where(). Nothing in them completes or navigates, an unknown entity or field is not reported, and getResult() is mixed where the query settles it (list<User>, or an array shape for a scalar select). PHPStan's Doctrine extension parses the DQL with Doctrine's own parser and the booted metadata; PHPantom would need a DQL reader of its own over the static mapping, with the query builder's chain followed the way T45's repository is.

Navigation and completion of the entity and field names are the cheaper half and the one an editor user notices; result types follow. The extension also types a query as Query<TKey, TResult>, so getResult() and its siblings follow from a Query passed in with its result type, and reads the expression builder's methods (expr()->isNull('u.email')) as the DQL fragment they build.

The extension's fixtures are tests/phpstan_doctrine/data/QueryResult/ for the types and the dql*.fixture and query_builder_dql*.fixture fixtures in tests/fixtures/phpstan_doctrine/ for the checks.

Where to look: src/framework.rs (the Doctrine mapping index), and PHPStan's Doctrine extension (Rules/Doctrine/ORM/DqlRule, QueryBuilderDqlRule, Type/Doctrine/Query/, Type/Doctrine/QueryBuilder/).

F45. Symfony events named by their class or a constant¶

Impact: Medium · Complexity: Medium

$dispatcher->dispatch(new OrderPlaced($order));   // which listeners?

#[AsEventListener]
public function onOrderPlaced(OrderPlaced $event): void {}

public static function getSubscribedEvents(): array
{
    return [KernelEvents::REQUEST => 'onRequest'];
}

An event name written as a string navigates between its dispatchers and its listeners. Most events are not: an event dispatched without a name is named by its class, an #[AsEventListener] without an event: subscribes to the class its method's first parameter is typed with, and a subscriber's map is usually keyed by OrderPlaced::class or a constant such as KernelEvents::REQUEST. None of these link a dispatch to its listeners. Symfony's own language server shows a CodeLens over an event class listing its listeners, and one over a listener listing its events, the way the Messenger lenses link a message and its handlers.

A constant key resolves to the string it holds, which also gives completion the framework's own events (kernel.request, console.command, security.interactive_login): only the names a project's listeners subscribe to are offered today, since nothing the installed bundles declare is read.

Where to look: src/symbol_map/extraction/symfony.rs (emit_symfony_listener_spans), src/symfony/messenger.rs (the handler side table to mirror), and references/symfony-language-tools (docs/features/events.rst).

F46. Symfony listener methods a tag or a default names¶

Two other ways of naming it do not: the method of a kernel.event_listener tag in YAML or XML, which names a method of the tagged service's class, and no method at all, where Symfony calls on followed by the event name in camel case, else __invoke(). F47. Symfony Messenger transports¶

Impact: Low-Medium · Complexity: Medium

framework:
    messenger:
        failure_transport: failed
        transports:
            async: '%env(MESSENGER_TRANSPORT_DSN)%'
            failed: 'doctrine://default?queue_name=failed'
        routing:
            App\Message\SendWelcomeEmail: async

A bus name navigates, completes, and is reported when nothing declares it. F48. Symfony environment variables¶

Impact: Medium · Complexity: Low-Medium

F55. Symfony ExpressionLanguage strings¶

Impact: Low · Complexity: Medium-High

#[IsGranted(new Expression('is_granted("ROLE_ADMIN") or user.isOwner(subject)'))]
#[Route('/admin', condition: "request.headers.get('X-Admin') == '1'")]

An ExpressionLanguage string is a small language of its own, with variables Symfony binds per site: user, subject, token, and request in a security expression, context and request in a route condition, the service container's functions in @= service arguments.
